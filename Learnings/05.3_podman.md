# Containerization with Podman & Docker

This documents my hands-on learning of containerization using **Podman**, while understanding Docker concepts and commands commonly used in DevOps environments.

## Image and Container Lifecycle Management

### Image Tagging and Versioning

Container image tags help manage different versions of an application.

Example:

```bash
podman tag my-custom-nginx:v1 my-custom-nginx:v1.0
```

Build a new image version:

```bash
podman build -t my-custom-nginx:v2 .
```

List available images:

```bash
podman images
```

Inspect an image:

```bash
podman image inspect my-custom-nginx:v1
```

### Image Layers and Caching

Container images are built using multiple layers. Each Dockerfile instruction contributes to the resulting image filesystem or configuration.

Podman reuses cached layers during subsequent builds when the relevant instructions and inputs have not changed.

Build without using cached layers:

```bash
podman build --no-cache -t my-custom-nginx:v2-test .
```

### Container Lifecycle Commands

| Command | Description |
|---|---|
| `podman run` | Create and start a container |
| `podman ps` | List running containers |
| `podman ps -a` | List all containers |
| `podman stop` | Stop a container |
| `podman start` | Start a stopped container |
| `podman restart` | Restart a container |
| `podman rm` | Remove a container |
| `podman logs` | View container logs |
| `podman inspect` | Inspect container configuration |
| `podman exec -it` | Execute commands inside a container |
| `podman stats` | Monitor container resource usage |

Run a container:

```bash
podman run -d --name custom-nginx-v2 -p 8082:80 my-custom-nginx:v2
```

Follow container logs:

```bash
podman logs -f custom-nginx-v2
```

Access the container shell:

```bash
podman exec -it custom-nginx-v2 bash
```

### Restart Policies and Health Checks

Restart policies help maintain application availability.

Common policies:

- `no`: Do not automatically restart.
- `always`: Always restart.
- `on-failure`: Restart after failure.
- `unless-stopped`: Restart unless manually stopped.

Example:

```bash
podman run -d --name restart-demo --restart=unless-stopped nginx
```

Configure a container health check:

```bash
podman run -d \
  --name health-demo \
  --health-cmd "curl -f http://localhost/ || exit 1" \
  --health-interval 30s \
  --health-timeout 5s \
  --health-retries 3 \
  nginx
```

Inspect health status:

```bash
podman inspect health-demo
```

## Container Networking

Container networking enables communication between containers and external systems.

### Important Networking Concepts

- **Port Mapping:** Exposes a container port through the host.
- **Bridge Network:** Connects containers through a virtual network.
- **Container DNS:** Resolves container or service names to network addresses.
- **Network Isolation:** Restricts communication between separate networks.

### Creating a Custom Network

List networks:

```bash
podman network ls
```

Create a network:

```bash
podman network create devops-net
```

Inspect the network:

```bash
podman network inspect devops-net
```

### Container-to-Container Communication

Run two containers on the same network:

```bash
podman run -d \
  --name net-nginx \
  --network devops-net \
  -p 8083:80 \
  nginx
```

```bash
podman run -d \
  --name net-nginx-internal \
  --network devops-net \
  nginx
```

Test communication using container DNS:

```bash
podman run --rm \
  --network devops-net \
  busybox wget -qO- http://net-nginx-internal
```

Containers connected to the same custom network can communicate using their container names.

The internal Nginx container does not need a published host port for this communication.

### Network Management Commands

| Command | Description |
|---|---|
| `podman network ls` | List networks |
| `podman network create` | Create a network |
| `podman network inspect` | Inspect a network |
| `podman network connect` | Connect a container |
| `podman network disconnect` | Disconnect a container |
| `podman network rm` | Remove a network |
| `podman port` | Display port mappings |

### Troubleshooting Networking

Check container status:

```bash
podman ps -a
```

Check port mappings:

```bash
podman port CONTAINER_NAME
```

Inspect network configuration:

```bash
podman network inspect devops-net
```

Check application logs:

```bash
podman logs CONTAINER_NAME
```

## Volumes and Persistent Storage

Container filesystems are generally ephemeral. Data stored only in a container's writable layer can be lost when the container is removed.

Persistent storage allows data to survive container recreation.

### Types of Storage

| Feature | Named Volume | Bind Mount |
|---|---|---|
| Storage location | Managed by Podman | Host directory |
| Creation | Podman | User |
| Persistence | Yes | Yes |
| Common use | Database storage | Application files and configuration |

### Named Volumes

Create a volume:

```bash
podman volume create devops-data
```

List volumes:

```bash
podman volume ls
```

Inspect a volume:

```bash
podman volume inspect devops-data
```

Attach a volume to an Nginx container:

```bash
podman run -d \
  --name volume-nginx \
  -p 8085:80 \
  -v devops-data:/usr/share/nginx/html \
  nginx
```

Create a file inside the mounted directory:

```bash
podman exec volume-nginx sh -c \
  "echo '<h1>Persistent Storage Works!</h1>' > /usr/share/nginx/html/index.html"
```

Remove and recreate the container using the same volume:

```bash
podman stop volume-nginx
podman rm volume-nginx
```

```bash
podman run -d \
  --name volume-nginx-new \
  -p 8085:80 \
  -v devops-data:/usr/share/nginx/html \
  nginx
```

Verify the previous data:

```bash
podman exec volume-nginx-new cat /usr/share/nginx/html/index.html
```

The file remains available because it was stored in the named volume.

### Bind Mounts

Bind mounts connect a host directory directly to a container directory.

Example using Windows PowerShell:

```powershell
New-Item -ItemType Directory -Force C:\DevOps\website
```

Create an HTML file:

```powershell
Set-Content C:\DevOps\website\index.html "<h1>Hello from Windows!</h1>"
```

Run Nginx with a read-only bind mount:

```powershell
podman run -d --name bind-nginx -p 8086:80 -v C:\DevOps\website:/usr/share/nginx/html:ro nginx
```

The `:ro` option provides read-only access inside the container.

Changes made to the host file are reflected in the mounted directory.

### Persistent PostgreSQL Storage

Create a named volume:

```bash
podman volume create postgres-data
```

Run PostgreSQL:

```bash
podman run -d \
  --name postgres-demo \
  -e POSTGRES_USER=appuser \
  -e POSTGRES_PASSWORD=<YOUR_PASSWORD> \
  -e POSTGRES_DB=appdb \
  -p 5433:5432 \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:16
```

Connect to PostgreSQL:

```bash
podman exec -it postgres-demo psql -U appuser -d appdb
```

Create a table:

```sql
CREATE TABLE employees (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100),
    role VARCHAR(100)
);
```

Insert a record:

```sql
INSERT INTO employees (name, role)
VALUES ('Ujwala', 'DevOps Engineer');
```

Retrieve records:

```sql
SELECT * FROM employees;
```

Removing and recreating the container with the same named volume preserves the database data.

### Storage Management Commands

| Command | Description |
|---|---|
| `podman volume create` | Create a volume |
| `podman volume ls` | List volumes |
| `podman volume inspect` | Inspect volume details |
| `podman volume rm` | Remove a volume |
| `podman volume prune` | Remove unused volumes |

**Best Practices:**
- Use named volumes for databases.
- Use bind mounts for development and configuration files.
- Avoid storing important data only in container writable layers.
- Maintain regular backups.
- Test database restoration.
- Avoid committing credentials to source control.

## Multi-Container Application Deployment with Compose

### Introduction to Compose

Docker Compose and Podman Compose simplify multi-container application deployment by defining services, networks, volumes, and configurations in a YAML file.

Instead of manually starting each container, the entire application can be managed through a single Compose configuration.

### Compose Architecture

The practical application contains:

- **Frontend:** Nginx reverse proxy.
- **Backend:** Python HTTP API.
- **Network:** Internal service communication.
- **Configuration:** Environment variables and health checks.

```text
              User Browser
                   |
                   | Port 8087
                   |
             +-----------+
             |   Nginx   |
             | Frontend  |
             +-----------+
                   |
                   | backend:8000
                   |
             +-----------+
             |  Python   |
             |  Backend  |
             +-----------+
```

### Project Structure

```text
compose-lab/
│
├── compose.yaml
│
├── backend/
│   ├── Dockerfile
│   └── app.py
│
└── nginx/
    └── default.conf
```

### Backend Application

The Python backend uses the standard library HTTP server to return JSON responses.

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import os
import json

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        response = {
            "message": "Hello from Python Backend!",
            "environment": os.getenv("APP_ENV", "unknown"),
            "service": "backend"
        }

        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        self.wfile.write(json.dumps(response).encode())

server = HTTPServer(("0.0.0.0", 8000), Handler)
print("Backend running on port 8000")
server.serve_forever()
```

### Backend Dockerfile

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY app.py .

EXPOSE 8000

CMD ["python", "app.py"]
```

### Nginx Reverse Proxy Configuration

```nginx
server {
    listen 80;

    location / {
        proxy_pass http://backend:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

The backend service name is used as the hostname through Compose's internal DNS.

### Compose YAML Configuration

```yaml
services:

  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    container_name: compose-backend
    environment:
      APP_ENV: development
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000')"]
      interval: 15s
      timeout: 5s
      retries: 3

  frontend:
    image: nginx:latest
    container_name: compose-frontend
    ports:
      - "8087:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      backend:
        condition: service_healthy
    restart: unless-stopped
```

## Troubleshooting and Best Practices

### Common Troubleshooting Commands

```bash
podman ps -a
podman images
podman logs CONTAINER_NAME
podman inspect CONTAINER_NAME
podman stats
podman port CONTAINER_NAME
podman network ls
podman network inspect NETWORK_NAME
podman volume ls
podman volume inspect VOLUME_NAME
```

### Common Problems

| Problem | Possible Cause |
|---|---|
| Container exits immediately | Application error or incorrect startup command |
| Website inaccessible | Incorrect port mapping or application failure |
| Connection refused | Service not listening on expected port |
| 502 Bad Gateway | Backend unavailable or incorrect proxy configuration |
| Database data lost | Missing persistent volume |
| Container communication failure | Incorrect network or service hostname |
| Compose deployment failure | Invalid YAML or missing Compose provider |
| Container unhealthy | Application or health-check failure |

### Container Security Practices

- Run applications using non-root users wherever possible.
- Prefer trusted and official base images.
- Use specific image versions rather than `latest` in production.
- Scan images for known vulnerabilities.
- Avoid running containers with unnecessary privileges.
- Use read-only mounts when write access is unnecessary.
- Store credentials using appropriate secrets management.
- Keep base images and dependencies updated.
- Avoid exposing internal services unnecessarily.
